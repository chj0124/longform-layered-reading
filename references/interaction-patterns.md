# 紧凑交互 HTML 规则

交互的目的，是让主线更短、关系更清楚、细节仍可回认。不是把长文换成一个需要不断点击的网页。

## 1. 页面骨架

单文件、无外部资源也能阅读：

```text
标题＋来源／范围
核心判断（短）
主线导航（可选，条目必须具体）
主阅读路径（默认直接可见）
  阶段问题
  具体回答与推导
  必要的关键证据／边界
  按需细节
收束
覆盖与验证说明
```

不制作占满首屏的封面、宣传式 Hero 或大段空白。读者打开页面后应尽快看到核心问题与回答。

## 2. 日常档模板复用

日常档优先复制 `assets/compact-reading-template.html`，替换标题、主线、细节、桥接和覆盖说明，不为每篇文章重新设计公共样式。

模板复用只减少设计成本，不免除当前文章实例的检查。模板过去的浏览器结果不能证明这次替换后的页面没有占位符、空细节、断链或内容错置。

需要完整档或回退时，记录结构／覆盖问题；如果变更公共模板、样式或交互，再执行相应完整呈现验证。只替换文章内容通常执行当前产物冒烟即可。

## 3. 主线与原生展开

- 主阅读路径不使用折叠，也不依赖 JavaScript 才显示。
- 二级理由、例子、数据、背景使用原生 `<details>/<summary>`。
- `summary` 写具体问题或内容，不写「点击更多」「展开详情」。
- 展开后必须有实质内容，不能再次只给抽象概括。
- 关键限定如果会改变主线结论，不得藏进细节层。

```html
<section id="stage-2">
  <h2>为什么预约后仍不能直接借用？</h2>
  <p>预约只处理工具保留；高功率工具还增加设备状态与操作边界两个条件。</p>
  <details>
    <summary>设备正常和异常时，分别会发生什么？</summary>
    <p>异常时不能交付；正常时仍需听完操作边界说明。</p>
  </details>
</section>
```

## 4. 具体桥接与导航

导航和图中的每个阶段尽量是问题或判断，而不是「第一部分」「分析」「原因」。

跨阶段连接写成：

```text
起点具体内容 → 推理／条件 → 终点具体内容
```

可用一行桥接文字、有序列表或简单关系图。箭头标签与正文一致，不能在图中写因果、正文却只说相关。

页内链接必须有对应 `id`。导航只是定位工具，不替代正文自身的推导。

## 5. 何时画图

至少满足一项再画：

- 两个以上主体分别行动并互相影响。
- 多条支线在后续汇聚，仅靠段落顺序难以看清。
- 存在反馈、循环或跨章节回指。
- 条件分支会导向不同结果。

若只是三层以内的并列大纲，树状文本通常更清楚。图形节点应使用原文具体概念，避免只有「问题—分析—解决」的通用外壳。

## 6. 响应式与可访问性底线

- 正文默认约 16px，行高适合中文长文阅读。
- 内容宽度有限，但移动端不挤压成窄列。
- 多列结构在窄屏降为单列；页面本身不横向溢出。
- 焦点清晰可见，链接与展开控件可通过键盘到达。
- 原生 `summary` 有明确可读名称，交互目标有足够高度。
- 不只靠颜色表达主线、细节或关系类型。
- 尊重减少动态效果偏好；无动画也不影响阅读。

## 7. 单文件与依赖

默认 CSS 内联，无 JavaScript 也能完成主阅读与展开。除非确有必要，不引入外部字体、脚本、图片或 CDN。

如果添加 JavaScript，只能增强定位、图形或审计等附加能力；脚本失效时主线与细节仍可访问。

## 8. 当前产物验证

日常档至少实际检查：页面可打开、主线直接可见、展开／关闭有效且非空、页内链接有目标、无占位符残留。

完整档或模板／交互变更时，按 `validation/cases/html-interaction.md` 检查桌面、移动、键盘、焦点、控制台与外部请求。变更哪一层，就重跑受影响的用例；不能把模板历史结果当作当前文章页面的验证结果。

## 9. 完整可回认

日常档按原文顺序逐段回查；完整档逐项核对信息单元落位。两种方式都要确保：

- 主线没有因排版而漏段。
- 每个折叠区有实际内容。
- 每个细节节点都有信息去向。
- 图中出现的新关系能在正文找到依据。
- 覆盖说明与执行档位一致，未做的测试不写通过。
