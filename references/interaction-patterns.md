# 交互模式：关系映射与固定实现要求

仅在步骤 4（输出候选含交互 HTML）加载。先按内容地图的关系选交互模式，再实现；交互不得反向创造逻辑。规则只覆盖基线与评分契约已固定的要求，不新增假设性禁令。

## 关系 → 交互映射（适用条件与反例）

### 1. 独立支撑 → 分支后汇聚

- **结构契约（正面规则，渲染前必须满足）**：
  1. 页面顶层分支必须是内容地图中的独立支柱，数量与之一一对应：顶层分支数＝独立支柱数，每条顶层分支对应一个支柱，不多不少。
  2. 支柱的支撑机制、实测案例、证据与子条件，一律渲染在其所支撑的支柱分支**内部**（作为该分支的展开内容），不得成为顶层分支。
  3. 分支数由内容地图决定：某篇文章的支柱数就是它的支柱数，不预设两个；只有内容地图判定为独立支柱的单元才配作顶层分支。
- **工作示例**：《为什么我对 Vibe Coding 软件毫无兴趣》的内容地图恰有两个顶层支柱——品质（审美阈值）与利他（正反馈消失）；拍档主题记账案例、协作岗拆解、三类内心意象等均为品质支柱的内部支撑，渲染进品质分支内部。利他分支内部同理收编匹配率三条件、慢鸽案例等。
- **验收检查（可观察）**：① 数顶层分支：数量必须等于内容地图的独立支柱数；② 逐个看顶层标签：任何支撑节点（机制、案例、证据、子条件）都不得带有顶层独立标签（如"理由N""支柱N"）。
- **交互形态**：并列分支节点视觉汇合到同一决定节点；每条分支可展开其证据、案例与限定条件。
- **反例**：排成单线链（理由A → 理由B → 决定，使一理由成为另一理由的前因）；把多个独立理由合并成一个理由；把支柱的支撑机制或实测案例列为顶层独立分支。

### 2. 必要前提 / 连续机制 → 顺序链

- **适用条件**：前一环节是后一环节成立的必要前提，或机制按原文顺序逐步展开。
- **交互形态**：顺序链逐节点展开，每个箭头可展开说明其原文依据。
- **反例**：把独立支撑误排成前提—结果链；箭头无原文依据；为显得有机制而添加原文没有的环节。

### 3. 共同作用 → 并列因素指向共同结果

- **适用条件**：原文呈现多个因素共同作用、指向同一结果。共同作用不要求每个因素必不可少：仅当原文明确确立各因素均为必要条件时，才使用必要性措辞；否则按贡献性因素并列呈现。
- **交互形态**：并列因素同层呈现，共同指向结果节点。
- **示例**：各因素共同促成结果，但单独缺失任一因素并不推翻结果（贡献性而非必不可少）时，仍用本模式呈现并列因素，不添加必要性措辞。
- **反例**：伪装成先后因果；把原文未确立为必要的因素写成互为必要条件；拆成彼此独立的支撑而丢失共同作用关系。

### 4. 反馈循环 → 循环图（受限使用）

- **适用条件**：仅当原文存在可回指的反馈路径（A 强化或削弱 B，B 又回指 A）时才使用循环图。
- **反例**：把单向先后画成循环；用循环图装饰没有回路的原文。

### 5. 对照 → 切换视图或对照表

- **适用条件**：两个以上主体、方案或情境共享稳定的比较维度（同一维度在各对象间含义一致）。
- **交互形态**：按钮切换视图（状态同步见下）或并列对照表；比较维度不稳定时改用结构化文字，不强行切换或制图。
- **反例**：列维度不稳仍用切换；把对照内容并入单线叙述而丢失并列。

### 6. 时间 → 时间线

- **适用条件**：事件按原文时间顺序发展。
- **交互形态**：时间线节点按序排列，节点可展开细节、引语与来源。
- **反例**：把时间先后写成因果（“X 导致/杀死了 Y”式）；打乱原文顺序。

### 7. 下钻（局部—整体、类别—实例）→ 展开 / 下钻

- **适用条件**：整体在默认层，局部细节或实例在下钻层；层级不过深（约 2—3 层以内）。
- **反例**：展开内容与默认层实质重复；为装饰制造无新信息的展开；层级过深导致主线被埋没。

## 关系图的资格、依据与数量（全部 HTML 输出必须满足）

1. **复杂逻辑必须可视化**：多支柱、前提链、共同作用、对照、反馈、时间和局部—整体等复杂关系，必须使用相应图形或交互视图，不得只留长段线性文字；图形须暴露关系，而非装饰正文。
2. **信息增益**：关系图必须减少或重组文字，或承载文字难以线性表达的关系；仅把卡片、标签、颜色摆成图形不算关系图，禁止用图形装饰冒充关系表达。
3. **逐关系有依据**：图中每条箭头与“独立”“汇聚”“缺一不可”等措辞都必须能在原文找到对应表述；原文只按顺序罗列多个论证时，按“共同作用／连续论证”呈现，不得画成各自独立、各自充分的分支汇聚。为暴露隐藏逻辑而补出的推断关系须用明确标签及区别于原文关系的样式标识。
4. **数量以不同关系为限**：每个视图至多一幅总览图；每个核心节点的每种不同关系至多一幅机制图或对照图。同一内容不得既以同等长度文字呈现、又以等价图表重复——图作概览时，文字只写图中没有的内容；不同复杂关系不得为凑少图而合并。

## 固定实现要求（全部 HTML 输出必须满足）

1. **单文件无依赖**：样式与脚本全部内嵌，不引用任何外部资源，双击即可打开。
2. **正文连续可读**：优化版 HTML 必须提供无需逐一操作控件即可阅读的正文与核心论证链；折叠用于辅助细节、背景和按需下钻，不得把正文全部藏起，迫使读者逐点点击才能了解原文。
3. **结构引导一致**：标题、编号、缩进、箭头和“前提／理由／证据／例子／推论／反驳／限制／结论”等标签须全篇一致；首次出现提供图例，不得只用颜色区分逻辑关系。
4. **展开新信息**：每个控件展开后呈现默认层没有的内容（细节、引语、限定条件）；禁止无信息增益的控件——无行为的按钮、空区块、仅装饰的切换一律不得出现。
5. **原生控件优先**：展开用原生 `<details>/<summary>`，互斥展开用同名 `name` 分组；确需 `hidden="until-found"` 时，必须监听 `beforematch` 同步相关控件状态，并对不支持的环境回退（展开全部内容并同步 ARIA 状态）；不给原生 `<button>` 再叠加 Enter/Space 键盘处理。
6. **键盘**：Tab 可达全部控件；自定义复合部件（如对照切换）支持方向键与 Home/End；保留可见焦点样式（`:focus-visible`）；焦点顺序符合阅读顺序。容器设 `overflow: clip/hidden` 时，内部控件的焦点框不得被裁切边界裁掉（如 details/summary 用负 `outline-offset` 把轮廓绘于边界内），且须在真实键盘 Tab 遍历中确认每个控件焦点可见，不得仅凭样式推断。
7. **ARIA 与语义**：ARIA 状态与实际行为一致（`aria-expanded` 等随真实开合同步）；每个 `aria-controls` 都有对应目标元素；使用真实标题层级（一个 h1，逐级不跳级）；标题不放在 `<summary>` 内（标题须作展开触发时用“标题包按钮”结构）；`<html lang>` 与内容语言一致。
8. **移动端**：响应式排版用 `clamp()` 组合视口与字号单位，不单独使用裸 `vw`；390×844 视口下无横向滚动、文字可读；可点目标不小于 24×24 CSS 像素，触屏环境进一步加大。
9. **如实报告**：默认层、逐节点展开、对照切换、键盘操作、移动视口与链接的实际浏览器检查未执行时，交付物必须声明未执行，不得声称已验证；页面内的验证声明（如页脚）同样只写实际执行的检查。
